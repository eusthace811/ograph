# ograph reference

## Commands

Every command takes `--root DIR` (the directory holding `.ograph/`, found by searching upward when omitted) and `--json`, which `serve` ignores because its output is the protocol. Exit codes follow ogrep: 0 when something was found, 1 when nothing was, 2 on error. Commands can run side by side on one store: `serve`, read commands and a harvest share `.ograph/store.redb`, and harvests and verdicts take turns through `.ograph/store.lock`.

| Command | What it does |
|---|---|
| `ograph init` | Creates `.ograph/` with `config.toml`, `ontology.ttl` and `shapes.ttl` |
| `ograph harvest [--only KIND]` | Runs the enrichers in layer order. The catalog, ownership and docs sources commit first, so later enrichers read the catalog this harvest leaves. Each source file becomes one named graph, except incidents, which all share one, then correlation runs for every incident. KIND is a kind from `config.toml` such as `config_changes`, its graph name such as `config`, or `correlation` |
| `ograph before INC [--window 10m] [--depth 4] [--known-at T]` | Events before an incident on its application and the applications it depends on (question 1). An episode that began up to 24 hours before the window and is still under way when it opens counts too. Operator actions reported in chat are listed with signal `OPERATOR_ACTION`, but correlation and `similar` signatures leave them out: an action before an incident opens is mostly a response to its first symptoms, and a deploy or rollback that changed code has its own deployment record. The scope follows a dependency the catalog dates (`ops:validFrom`) only if the incident opened at or after that date; `withheld` lists each one it did not follow from an application nearer than `--depth`, as `caller`, `callee` and `valid_from`. An event whose series (same application, signal kind, and metric or log template; deployments, changes and alerts have none) started at least 2 episodes in the correlation window (`window_s`, 30 minutes by default) before the incident opened carries `chronic`, a sentence with the count, for example `redis diskio fired 4 times in the 30 min before the incident: likely background, not a new fault`; the text output prints it under the event. Only events the view holds count, so `--known-at` applies, and `--window` does not change the lookback |
| `ograph chains INC [--rank chain\|propagation] [--window 30m] [--top 5] [--set k=v] [--known-at T \| --since T]` | Ranked root-cause applications, each with its best chain. A chain's id, such as `id:chain/inc-5377-e1fef786a90c3b12`, comes from its incident and root event, so it names the same hypothesis after any re-correlation. The number printed before an application is its chain's `corr:rank` after a harvest with the configured settings; a harvest stores the chains of the first `max_chains` applications, each with `corr:settings`, a hash of the settings that ranked it. Each chain carries `scores`, one entry per event of the chain, root first, for the link that leaves it; the last one closes the chain at the incident. An entry has `from` and `to` (`application:SIGNAL`, or `incident`), `time` (time proximity), `severity`, `known_pair`, `edge` and `score`. `score` is `known_pair_prior` when `known_pair` is true and `w_time * time + w_severity * severity` otherwise, and the chain's `confidence` is the geometric mean of the scores. `edge` says where the dependency the link crosses comes from: `same_app` (none crossed), `catalog` (declared, or inferred by ogrep from configuration), `trace` (only parent spans state it), `other`, or `indirect` (the link closes at the incident from more than one hop away). `weakest` is the first link with the lowest score. The text output prints one line per link and names the weakest link of a chain with more than one. A `root` or `links` event whose series fired again and again before the incident carries `chronic`, as in `before`, over the window the chains use; the text output prints `chronic APP:SIGNAL: ...` under the chain. The mark does not change any score or rank. When the store holds verdicts, an application carries `precedent` if its chain's root has the application and signal of an accepted cause of one of the three most similar past incidents that have one: that incident, its `similarity`, the cause's `app` and `signal`, and the verdict's `evidence`. With `precedent_weight` above 0 the application's `score` also gains the weight times that similarity, so it can exceed 1; a chain's `confidence` never changes. With a weight, a new verdict changes the ranks `chains` prints for similar later incidents at once and their stored `corr:rank` at the next harvest, so until then record a verdict on such an incident by chain id, not by rank. Like `before`, it follows a dated dependency only for an incident that opened at or after its date, and `withheld` (left out when empty) lists the ones it did not follow; the text output prints each as `not followed`. When no application ranks and a `code` source is configured, the answer also carries `suspects`, the list `ograph suspects INC` gives, and the exit code is 0 when that list is not empty |
| `ograph code INC [--top 5]` | Where an incident points in the code. `locations` are the lines behind its candidate events: the log bursts and exceptions that carry `evt:codeLocation`, newest first. `commits` are the candidate commits. Those that changed a located file come first, and `touches` lists those lines. `deployments` are the candidate deployments that carry changed files, listed the same way. A located log message also gets `introduced`, the commit that first added it to the code among the commits made until the incident, with `days_before`. That lookup needs `ogrep index --history` in the repository, and `degraded` says so when the index is missing. `files` are the files the incident's description is about, and `writeups` are the past incident write-ups that share its words. ogrep ranks both in every `code` repository, and `--top` limits them. The description is the incident title, then the applications and messages along the top-ranked chain. Candidate events come from the configured correlation window. A repository ogrep cannot answer for is named in `degraded`. Without a `code` source `files` and `writeups` are empty |
| `ograph suspects INC\|APP[,APP...] [--since WHEN]` | Likely causes from the dependency graph and recent commits, with no telemetry. It runs `ogrep --suspects` in each `catalog` and `code` repository and uses the first that answers. For an incident, the failing applications are its own and those of the other incidents opened within the correlation window of it, and commits count from the day before it until it opened. ogrep 0.2.0 cannot stop at a time, so with it later commits count too and a note says so. For application names, commits count from 24 hours ago. `--since` takes what ogrep takes: `24h`, `3d` or a date such as `2026-11-22`. A repository ogrep cannot answer for is reported on standard error |
| `ograph blast APP [--depth 8] [--at WHEN] [--known-at T]` | Dependents by distance, the business processes they support, and open incidents (question 2). With `--at`, only through dependencies that held at WHEN: an incident (its opening time), an `xsd:dateTime` with a zone, or how long ago. A dependency the catalog does not date holds at every time. With `--at`, the open incidents are those that had opened by WHEN and were not resolved by then; one with no resolved time follows its status |
| `ograph similar INC [--top 5]` | Past incidents with the same signature, with their accepted causes and mitigations (question 3). An incident with telemetry is compared by the applications and signals before it; what the incidents state (the application, `fault` and `inc:faultClass`) then orders the matches, by reciprocal rank fusion of the two rankings. An incident with no telemetry is compared by what it states alone. `similarity` is the cosine of the signature that chose the matches. `ruled_out` lists the roots a verdict rejected on each: `app`, `signal` and the verdict's `evidence`. It is what that incident was found not to be, and it does not change any ranking. Mitigations are the incident's `mitigation` field, then the operator actions taken in it, by time, as `KIND app at TIME: quote`: those with `evt:during` the incident, and those on its application from its open time until its resolved time (or for `window_s` when it has none) |
| `ograph news [--since DURATION]` | News that mentions a vendor our applications use (all of it by default, or only the last DURATION, such as `7d`), with the affected applications and processes (question 4) |
| `ograph why NODE` | Provenance of every fact about a node: the harvest graph, source, extractor and time, model provenance, and quarantined proposals. For a chain it also lists every verdict on it, oldest first, with its state, who gave it, when, its evidence, the rank the chain had then, and whether a later verdict superseded it (`verdicts` in `--json`). For a detected event, `chronic` says when its series started at least 2 episodes within the correlation window of it, before or after |
| `ograph uses PATH[#n]` | What depends on a source file, a directory of them, or one record (`PATH#n`, `PATH:n`, `PATH@n`), for when a source turns out to be wrong. A path is relative to the current directory, read as written (`sub/../alerts.json` is `alerts.json`, and `.` at the workspace root is every source). It lists the file's facts, each with `also_in`, the other sources that state the same fact (a fact with none goes with the file); the events and incidents no other source states; `shared`, the incidents it states together with records of other incident files, which stay; and the facts of other sources that their next harvest would quarantine without it, each with `because`, such as an operator action whose `evt:during` incident goes. A shared incident keeps only the facts another record states: a field only this file sets goes, and SHACL then checks the incident again, so one left without its application or time is quarantined, goes with its chains and is no longer `shared`. Then the chains: every incident is ranked again over the store without those facts and compared with the ranking over the store, as a harvest would store them, so a chain that changes through a dependency the file states is found too. Each chain has `change` (`gone`, `relinked` for another root or set of links, `moved` for another rank, or `new`), `rank` and `rank_after`, and `uses`, its root, links and incident that go with the file. A field another record states with a different value takes that value at the next harvest; the ranking here leaves the field out instead. `verdicts` holds the current verdict on each chain that goes or is relinked, and `quarantined` the quarantined proposals the file or record made, or whose reason names it, such as a value that disagrees with one it states. In a graph of several files (incidents) a fact is traced to its file through `evt:sourceRecord`: every incident carries one per record that states it, and each fact of an incident that more than one record states has a provenance node (`harv:fact`, `harv:method "rule"`) with an `evt:sourceRecord` per record that states that fact. A store harvested before this version lacks them, and `warnings` (also printed on standard error) says to harvest once. With a record, only the nodes that name it in `evt:sourceRecord` are traced: events, incidents, chat threads (one `evt:sourceRecord` per message) and model facts, with the facts they describe, not, for example, an ownership line. A thread that keeps other messages stays in `shared`, and `warnings` says that its text, and so the model's answers on it, change in ways the answer does not predict. A file of a naming source (`catalog`, `ownership`, `docs`) gets `naming`: every other file's names are checked against it, so without it facts elsewhere can change in ways the answer does not list, and a catalog's facts are not traced to its files. Removing a file means deleting it and, when its `[[source]]` names it or a directory it was the last file in, that entry too: ograph keeps the last facts of a configured path it cannot read. Exit 1 when the store holds nothing from it |
| `ograph resolve NAME...` | Up to 5 application names, aliases or IRIs to catalog applications, by the gateway's catalog rules (below). Each is `resolved` (an exact name or alias, or a fuzzy match the gateway would accept), `ambiguous` (a match the gateway would quarantine as ambiguous: a sibling, a tie, or a score from 0.80 to 0.93) or `unresolved`, with the rationale and up to three candidates with their Jaro-Winkler scores. Names past the fifth are listed under `skipped`. Exit 0 when one resolved |
| `ograph cite-check FILE\|-` | Checks what an answer cites against the graph now. Chain ids, incident ids (shaped like the graph's own, such as `INC-5377`), IRIs (`id:...` or full) and application names are each `present`, `stale` or `unknown`. A chain is stale when it has a rank other than the one written next to its id (`id:chain/x is rank 2`, `id:chain/x (rank 2)` or `rank 2: id:chain/x`; a list number such as `3.` is no rank), or when correlation no longer produces it but its root event is still in the graph or a verdict names it. A chain id no event of its incident produces is unknown. A word with `-` or `_` that the gateway would not accept as an application, such as `ledger-db-canary` or `legacy-ledger-db`, is an unknown application; a plain word counts only when it is a catalog name or alias. Exit 0 when every citation is present |
| `ograph status` | One line when something is due, nothing otherwise: source files and settings changed, added, deleted or renamed since the last full harvest began (a full harvest records that time and the files it read in `.ograph/harvested`; `--only` does not; a marker from an older ograph holds only the time, so until the next full harvest only edits are seen), and incidents with chains but no verdict. It opens the store without writing to it. `--json` gives `harvested_at`, `changed` and `unjudged`. Exit 0 when something is due. `./x install-hook` makes it a Claude Code `SessionStart` hook |
| `ograph verdict CHAIN accept\|reject --evidence REF --by WHO` | Records a human verdict on a chain id, or on `id:chain/<incident>-<rank>` for the chain at that rank now. Any other name that is not a chain is an error. The verdict keeps the chain's incident and root event, and stores the root's class, application, time and signal on the verdict node (`rca:rootClass`, `rca:rootOn`, `rca:rootAt`, `rca:rootSignal`), so it means the same after re-correlation or after the root's telemetry leaves the sources. A root whose telemetry is gone is no longer a candidate for correlation or `before`, except in a view of a time when the store still held it (`--known-at`, below). It also stores the rank the chain had and the hash of the settings that ranked it (`rca:rank`, `rca:settings`). Judging a chain again adds a verdict: the first is `id:verdict/<chain>`, the next `id:verdict/<chain>-v2`, and each earlier one gets `rca:supersededBy` the one after it. The verdict nothing supersedes is the current one. Only the current verdict counts: an accepted one writes `inc:cause`, and `similar` and `replay` read only it. `[verdict]` in the configuration can require evidence |
| `ograph replay [--set k=v]` | Correlates every incident that has a current verdict twice, under the configured settings and with the `--set` overrides (as `chains` takes them), on the data in the store now. It lists the verdicts each ranking contradicts. A ranking contradicts an accepted verdict when the root's application is not ranked first: `lost rank 1`, or `dropped out` when the application is not among the `max_chains` applications a harvest stores. It contradicts a rejected verdict (`rose to rank 1`) when the rejected chain itself is ranked first, because the verdict judged that chain, not the application. A flip is a verdict that the configured settings agree with and the overrides contradict, and a fixed verdict is the reverse. Run it with the change as `--set` before you edit `config.toml`: it exits 0 when no verdict flips and 1 when any does. Without `--set` nothing can flip, and the output lists the verdicts the current settings already contradict. `--json` gives every verdict with the rank it had when judged and its application and chain ranks under both settings. It also counts stored chains whose `corr:settings` is not the configured settings' hash, which the next harvest re-ranks |
| `ograph sparql 'QUERY' [--limit N] [--known-at T]` | Runs SPARQL 1.1. The prefixes are predeclared, and the default graph is the deduplicated union of all harvests. A class or property in an ograph namespace that the ontology does not declare is an error that names the nearest declared one. Each node stores only its most specific type, so a class with subclasses, such as `evt:Event`, is an error that lists them |
| `ograph validate` | Runs a full SHACL audit of the store. It also prints how many focus nodes each `shapes.ttl` shape with a target selects, and warns about the shapes that select none, whether misspelled or waiting for data that never came. Exits 1 only on violations. `--json` gives `{"violations", "shapes", "unmatched"}` |
| `ograph export [--out FILE]` | Writes every named graph as TriG |
| `ograph ontology check` | Checks drift between the code and the ontology. Problems, which exit 1: a term the code uses that the ontology does not declare, a property whose domain or range is undeclared, and a class or property in `shapes.ttl` that the ontology does not declare. Warnings, which never change the exit code: a property without a domain or a range, a class or property without an `rdfs:comment` or still marked `Proposed:`, a declared term no code writes (event classes and `evt:signal` values against the enrichers' list, other terms against the code's names), a class or property the store has none of, and an event class no `shapes.ttl` shape requires an `evt:at` of. `--json` gives `{"problems", "warnings"}` |
| `ograph ontology diff NEWER.ttl [--shapes FILE]` | Compares the workspace's ontology with a newer one, and its `shapes.ttl` with `--shapes FILE` (default: the workspace's own). Give either or both. It lists the changes, and marks one BREAKING when stored data uses what it removes or narrows: a removed class, property or vocabulary value, a closed vocabulary, a class that loses a superclass, a property that becomes functional, or a domain or range that is not a superclass of the old one. The same change to a term the store never uses is marked `(unused)`. A domain or range that moves to a superclass, or is dropped, is widened. Then it puts each stored harvest graph through the ontology checks and SHACL under both versions, and prints, per graph, how many facts a harvest under the newer one would quarantine and why. Verdict graphs are reported apart: no harvest rewrites them, so their facts are not quarantined, but a new `ograph verdict` on such a chain re-adds the earlier verdicts' facts and is refused. Exits 1 when any change is BREAKING, any fact would be quarantined or any verdict fact is no longer valid. `--json` gives `{"changes", "quarantine", "verdicts"}` |
| `ograph ontology coverage QUESTIONS [--out FILE]` | Needs a model. For each question in the file (one per line), it reports the declared names that represent it and the concepts nothing declared represents. Gaps go to `.ograph/proposed.ttl` as Turtle for a person to review, merge into `ontology.ttl`, then check with `ontology diff`. A gap a person has declined in `.ograph/declined.ttl` is reported as `declined by WHO` and never proposed again. Exits 1 when any question has a gap nobody has judged, or got no answer |
| `ograph lab [--out FILE]` | Writes one self-contained HTML page (no server, no external files, light and dark themes, readable at phone width). Per incident: the ranked causes with their chains; a timeline with one lane per application in scope, nearest dependency first, each event a bar from its start to its end, the incident as the zero line and the top chain as arrows; the dependency neighbourhood (dependencies up to the correlation depth, and the callers of the top cause) with the applications that had events filled and the top chain outlined; the evidence of every event in the top five chains, as `ograph why` gives it, with the chain's verdict and an `ograph verdict` command to copy; the events table and similar past incidents. Events and chain events marked `chronic` (as in `before`) say so after their strength. The SVG is drawn when the page is written, so it reads with scripts off; the script only opens evidence, filters the timeline to an application clicked in the neighbourhood, and copies the command |
| `ograph changes --since T` | What the sources state differently now than at T: each fact added (`+`), removed (`-`) or changed (`~`, one value of a subject's property replaced by another), with when ograph recorded it and the graph, source and extractor it came from. See [What ograph knew at a time](#what-ograph-knew-at-a-time) |
| `ograph stats`, `ograph compact` | Shows size per table, or drops history older than `history_days` and rewrites the store file without free pages |
| `ograph serve [--addr A]` / `ograph serve --mcp` | Serves line-delimited JSON-RPC over TCP, with the address in `.ograph/serve.json`. Every 5 s it compares the path, modification time and size of each file a harvest reads (for a catalog, the YAML and `.env` files `ogrep --files` lists, so ignore rules apply; for a `code` repository, only `.git/logs/HEAD`, which changes with every commit, pull and checkout), plus `config.toml`, `ontology.ttl` and `shapes.ttl`, and re-harvests on any addition, edit or deletion, retrying a failed harvest at the next poll. With `--mcp`, serves MCP over stdio without polling: the same tools plus `resolve` and `cite_check`, each with `annotations.readOnlyHint` (false only for `verdict`); the resources `ograph://ontology` and `ograph://incidents` and the template `ograph://incident/{id}` (`before`, `chains`, `similar`, and `blast` for the top-ranked application); and the prompt `investigate {incident}`, built from `skills/ograph/references/investigation.md` |

A node name may be any of these:

- an IRI
- a prefixed name such as `id:inc/inc-5377`
- an incident id such as `INC-5377`
- an application name or alias

A node whose facts have all left the store is not found (`nothing in the graph is called INC-5377`), and one whose facts are all in quarantine is an error that gives their reasons. `why` still shows a quarantined node's proposals.

### What ograph knew at a time

A harvest replaces each graph with what its file says now. What it removes goes to a history in the store, with the time ograph held it. `--known-at T` on `before`, `chains`, `blast` and `sparql` answers from the store as it was at T: facts recorded after T are hidden and facts removed after T are back. `chains` and `before` compute their answer again over that view, so `chains INC --known-at T` prints what `chains INC` printed at T, given the same settings. T is an `xsd:dateTime` with a zone, such as `2026-11-25T09:30:00Z` or `2026-11-25T10:30:00.123456+01:00`, or how long ago, such as `90m` or `2d`. ograph records times to the millisecond, so finer fractions round down.

- **The time is when ograph recorded a fact, not when it became true.** A dependency that the catalog gained last week and ograph first harvested today is known from today.
- **Only harvested episodes come back.** The view holds what a harvest recorded and the history still keeps. Raw telemetry was never in the store. `ograph compact` drops history older than `history_days`, and a T before the history starts is an error, not a partial answer. A T written to the whole second may name the second the history starts in, though the history starts some milliseconds into it; a T with milliseconds must not be earlier than the start.
- **A node recorded after T was not known at T.** `chains INC --known-at T` for an incident first harvested after T says so instead of answering; `chains INC --since T` ranks nothing then, as it does for an incident known at T without its application or time.
- **A retired root is a candidate again in a view of a time when the store held it.** Without `--known-at`, a root whose telemetry left the sources is not a candidate.
- **The fallback suspects of `chains --known-at` come from the code as it is now.** When no application ranks in the view, `suspects` reads the repositories of the `code` sources at their current revision, not as they were at T.
- **Standard output is the answer; standard error says what the view covers**: how many quads it hides and restores, and when the history starts.
- **Cost.** The history grows by one row per quad a harvest removes or adds to a graph that already existed. A first harvest and an unchanged harvest add none. Building a view reads the history and every graph first written after T, and keeps both in memory; the time index describes the store now, so a view finds events by application without it.

`ograph changes --since T` lists the difference between that view and the store now. It leaves out harvest bookkeeping (`harv:` facts), quarantined proposals and chains, which are recomputed from the facts it lists. A fact that moved between files, or left and came back, is not a change. `serve`, `similar`, `why`, `code`, `news` and `lab` answer only from the store now.

`ograph chains INC --since T` answers why the ranking moved. After the usual output it ranks the incident again in the view of T and prints the top `--top` applications then and now. When their order differs, it tests each source file that changed since T, one at a time, on the same state of the store:

- **`needed`**: the store now with only this file taken back to T ranks differently from the store now.
- **`enough`**: the store at T with only this file brought forward to now ranks differently from the store at T.

A file is named when either test holds. `--json` adds `shift`: `since`, `then` and `now` (each `app` and `score`), `changed_graphs`, and `causes` (each `graph`, `source`, `needed`, `enough`). The tests rerank the incident, so the names are computed, not inferred from the facts `changes` lists.

- **A moved ranking is a different order of the top `--top` applications.** A score that changed without changing the order is not a move, and when the order did not move no file is tested or named, even if two changes cancel out.
- **Interacting changes.** Two files that hold the same evidence are each `enough` and neither `needed`. A change that moves the ranking only together with another, such as a score that drops below a candidate another file added, is named with the mark of the test it passes. When the files move the ranking only together and each is neither `needed` nor `enough`, none is named and the output says the changes move it together.
- **Chains and quarantine are not tested.** They follow from the files; a view keeps them as the base view has them.
- **Cost.** Two rankings for each changed file, over one read of the history. On a store of the 90 RCAEval cases, one `chains --since` process took 18 ms with 1 changed file, 61 ms with 9 and 725 ms with 88, against 13 to 15 ms without `--since` (`docs/evidence/chain-delta.txt`).

## Configuration (`.ograph/config.toml`)

A key or table that ograph does not know, such as `[corelation]` or `windw_s`, is an error.

```toml
history_days = 90           # days of removed facts that `ograph compact` keeps; above the first table

[[source]]
kind = "catalog"            # one table per input, any order
path = "repo"

[detect]
metric_z = 5.0              # robust z threshold for metric episodes
metric_baseline_s = 300     # trailing baseline window, widened for coarse series to hold 12 points
metric_min_run = 3          # consecutive anomalous points that make an episode
metric_min_history_s = 150  # seconds of history before the detector judges a point (no warm-up episodes)
log_burst_factor = 3.0      # error-template count vs. the 5-minute trailing mean
log_min_count = 3
log_new_after_s = 600       # a message absent from this much of a service's log is new at its first error line; 0 turns it off
trace_error_rate = 0.05
trace_slow_factor = 2.0     # p95 vs. the trailing median p95
two_sided = ["workload", "throughput", "requests"]  # metrics where a drop also counts

[correlation]
window_s = 1800             # 30 minutes (Netflix uses 10; see docs/EVIDENCE.md)
after_s = 0                 # seconds after the incident still searched; such an event closes its chain at the incident
min_confidence = 0.6        # Netflix: chains under 0.6 are discarded
w_time = 0.6                # Netflix: time_proximity * 0.6 + severity * 0.4
w_severity = 0.4
known_pair_prior = 0.9      # Netflix: known causal pairs carry a 0.9 prior
rank = "chain"              # or "propagation"
prop_weights = [0.4, 0.5, 0.1, 0.0]  # propagation: strength, chain, spread, onset
signature_window_s = 900    # the window `similar` compares
precedent_weight = 0.0      # added to a root's score, times similarity, when a similar past incident's accepted cause has its application and signal; 0.01 only breaks near-ties (docs/EVIDENCE.md)
depth = 4                   # dependency hops in scope
max_chains = 10             # ranked applications whose chains a harvest stores

[verdict]                   # what evidence a verdict must cite; the defaults take any verdict
require_evidence = false    # refuse a verdict with no --evidence (one without is stored as "(none given)")
evidence_patterns = []      # regular expressions, e.g. ['^PM-\d+$']; at least one piece of evidence must match one
evidence_in_store = false   # at least one piece of evidence must name a node in the graph, as `ograph why` resolves it

[incidents]                 # optional; how a field stated by several records is chosen
merge = { at = "earliest", severity = "max" }  # default = "last" for every field

[llm.extract]               # optional; without it, discussions get regex facts only
command = ["pi", "-p", "--no-tools", "--no-session", "--no-extensions", "--no-skills",
           "--no-context-files", "--offline", "--thinking", "off", "--model", "openai/gpt-6-luna"]
model = "pi:openai/gpt-6-luna"
parallel = 4
timeout_s = 90
```

## Input formats

Times may be any of these:

- Unix seconds, milliseconds, microseconds or nanoseconds, as a number or a numeric string. The magnitude picks the unit: below 10^10 is seconds, below 10^13 milliseconds, below 10^16 microseconds, and anything larger nanoseconds
- ISO 8601 with any fraction and offset (`Z`, `+05:30`, `+0530`, `+05` or a trailing ` UTC`); no offset means UTC

A time must fall between 1971-01-01 and 2200-01-01. ograph rejects any other value, such as `nan`, `inf`, a bare year (`2026`) or a compact date (`20261122`), and treats the record as having no time.

JSON inputs may be a JSON array, one object, or JSON lines.

| `kind` | Format | Facts it proposes |
|---|---|---|
| `catalog` | Required. A git repository. ograph runs `ogrep --entities . --json` in it, which reads Backstage, Compose, Kubernetes and Prometheus rules, so `ogrep` must be on `PATH`; set `OGRAPH_OGREP` to point at another binary. Only the catalog creates applications, so without it every fact about a service is quarantined. Optional `inferred` (default `true`) also takes the calls ogrep infers from configuration, such as an environment variable that holds another service's address. Kubernetes manifests declare no dependencies, so there the inferred calls are the whole graph. Set `inferred = false` to keep only what a file declares. ograph also runs `--dated`, which gives each dependency the main-line commit since which the repository has held it. A dependency added to a service the files already declared gets that commit's time as `ops:validFrom`, and `before`, `chains`, the lab and `blast --at` follow it only for a time at or after it. A dependency that came in the commit that declared its service gets no date, because before that commit the files said nothing about the service: a catalog first committed today does not withhold its dependencies from last year's incidents. Neither does a dependency only the work tree holds. A pair stated by several edges or files holds from the earliest, and at every time if one of them is undated. An ogrep that cannot date (0.3.0 and older) still works: every dependency then holds at every time, and the harvest marks the catalog degraded with `dependencies carry no date`. The dating reads the operations files of every first-parent commit that changed one: 1.3 s on microservices-demo (502 such commits) and 1.9 s on opentelemetry-demo (802), against 0.05 s without it (`docs/evidence/edge-dates.txt`) | `ops:Application`, `ops:name`, `ops:dependsOn` (declared, or inferred from a call), `ops:alias` for a Kubernetes Service that fronts a workload with another name (ogrep 0.3 or newer), `ops:Dependency` with `ops:caller`, `ops:callee`, `ops:validFrom` and `ops:addedIn` (the commit) for a dated dependency (ogrep after 0.3.0) |

| `docs` | Runbooks and other prose, Markdown or text | `ops:alias`, only from a phrase that states one: `A, also known as B`, `A aka B`, `A (aka B)`, `A, formerly B`, `A is also called B`, or `A (b-c)` where the parenthesis holds a kebab or snake identifier that does not end in a number and shares a part other than `api`, `svc` or a similar word with `A` |

The fields are merged before they are checked, so an incident whose service is in one file and whose open time is in another is whole after one harvest. `[incidents] merge` chooses another record per field: `at` (open time), `resolved`, `severity` and `service` take `last` or `first`, the two times also take `earliest` or `latest`, and `severity` also takes `max` (most severe) or `min`; `default` sets the rest. | `errors` | `{"service", "at", "message", "stack", "level"?, "count"?}` from an error tracker. `app`, `time`, `timestamp`, `ts`, `error`, `title`, `stacktrace`, `trace` and `severity` also work | `evt:Exception` with mapped severity (SEV3 when the record states none). Every event carries its evidence: `file#record`, `file:line`, `file@ms` or, for a commit, `repository@revision`. `ograph why` shows it.

### Code

ograph asks ogrep about code and keeps only pointers. Paths are relative to the workspace root.

| Term | Meaning |
|---|---|
| `evt:Commit` | A commit to a service's code or configuration. Signal `COMMIT`, severity SEV4 |
| `evt:Exception` | An error report with a stack trace. Signal `EXCEPTION` |
| `evt:revision` | The full commit id |
| `evt:changedFile` | A file a commit changed, or a deployment changed since the version before it |
| `evt:codeLocation` | `path:line` of the code behind an event: the statement that writes a log template, or a frame of a stack trace |

- **Correlation.** A commit is a candidate event like a deployment and scores by the generic rule. `ograph code` shows which commits changed the file behind a later event; chain scores do not use that (docs/EVIDENCE.md).
- **Speed.** Run `ogrep index .` in the code repository to make these lookups fast, and `ogrep index --history` so `ograph code` can name the commit that first added a message. ograph builds neither index. Without the first ogrep scans every file and prints a warning; without the second `ograph code` lists the reason under `degraded`.
- **Failure.** A missing or failing ogrep never fails a harvest or a query. The harvest line says `DEGRADED`, the events are kept without code locations, and the queries list the reason.

## The gateway

Enrichers never write to the store. A batch goes through these checks in order:

1. **IRI scheme.** IRIs must have the form `https://ograph.dev/id/<kind>/<slug>`.
2. **Catalog.** Applications and teams must resolve against the catalog:
   - an exact name or alias is accepted;
   - a fuzzy match at Jaro-Winkler 0.93 or above is accepted and counted (tied scores go to the first IRI in order), unless another entity scores within 0.03 of it or the name is a sibling: the same words but one, and that word unlike its counterpart (`inventory-service-uk` against `inventory-service-eu`, `v1` against `v2`), or the same words plus more that are not filler such as `svc` or `api` (`inventory-service-eu-canary` against `inventory-service-eu`). Those are quarantined as ambiguous;
   - a match from 0.80 to 0.93 is quarantined as ambiguous;
   - anything lower is quarantined as missing.
3. **Catalog-only types.** Only the catalog may create an application.
4. **Ontology membership.** Only ontology properties and classes are allowed.
5. **Closed vocabularies.** Values must come from the vocabularies declared in `og:vocabulary`.
6. **Model confidence.** A model's confidence must be at least 0.5. The `Llm` variant cannot exist without one.
7. **Model-proposed structure.** A model may propose `ops:dependsOn` only when the catalog or traces already hold the same edge. Otherwise the edge is quarantined as unconfirmed.
8. **Aliases.** An alias that already names a different application is quarantined, and so is an alias that two applications claim in one batch, for both of them.
9. **Evidence.** Each fact needs evidence that names a record this harvest read.
10. **Incremental SHACL.** Shapes run on the nodes the batch touches, seen as the store will be after the commit. They are the derived domain, range, datatype, vocabulary and functional shapes, plus `shapes.ttl`. A violation that no single fact caused, such as a missing required value, rejects the node. A bad value that another graph holds, such as a verdict's cause, is not the batch's fault and rejects nothing. An end time before its start (`evt:until` or `inc:resolvedAt` before `evt:at`, from `shapes.ttl`) rejects the end time alone, so the event or incident keeps its place on the timeline. The checks repeat until no violation is left.

Rejected facts go to `g:quarantine/<source>/<key>` with their reason, and so do facts an enricher withholds itself, such as the incident values a merge did not keep. Accepted facts replace `g:harvest/<source>/<key>`, and only the difference is written, so an unchanged re-harvest writes nothing, and a graph's `harv:at` is when it last changed. What the difference removes is kept in the history (see [What ograph knew at a time](#what-ograph-knew-at-a-time)). The key is the file's path relative to the workspace, percent-encoded but otherwise kept, so two files never share a graph. Incidents are the exception: every file of every `incidents` source is one batch with the key `all`, in `g:harvest/incidents/all`, and each fact's evidence still names its `file#n`. If any incident file cannot be read, any incident source path cannot be listed, or an incident directory that held files lists none, that batch fails and every incident keeps its last good facts. The incidents graph records each file it read as `harv:file`. A file that cannot be read at all, or is empty, keeps its last good facts and is marked degraded. A full harvest clears the graphs of files that no longer exist, of sources no longer configured and of incidents that no longer have chains; verdicts are never cleared, and `--only KIND` clears only that kind's and then re-correlates and fails on a kind that is not configured. Input graphs are cleared before any batch is checked, and chain graphs after correlation, so one harvest leaves the store as two would. A source path or a directory below it that cannot be listed reports one degraded batch and keeps the graphs of every file under it, and only those: a sibling source of the same kind is still pruned. A source directory that lists no files while the store holds graphs under it, such as an unmounted mount point, is treated the same way.

## Declined proposals (`.ograph/declined.ttl`)

A person who decides the ontology will not have a proposed term records it in `.ograph/declined.ttl`, kept in git beside `ontology.ttl`:

```turtle
@prefix og: <https://ograph.dev/meta#> .
@prefix ops: <https://ograph.dev/ops#> .

ops:KubernetesCluster og:declined "We model services, not the clusters under them." ;
  og:by "dana" ;
  og:question "Which Kubernetes cluster runs payments-api?" .
```

The subject is the term as `proposed.ttl` named it. `og:declined` gives the reason and `og:by` who decided; a term without `og:by` is an error. The decline covers the gap that would be proposed under that name, for any question. Under each `og:question`, which can repeat, it also covers a gap whose words contain the term's words or are contained in them, since a model may quote "cluster" in one run and "Kubernetes cluster" in the next.
