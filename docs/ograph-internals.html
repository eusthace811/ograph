How ograph works inside

The data model, the quad store, the validation gateway, the detectors and the correlation engine, with the measurement behind each design choice. If you are new to ograph, read the plain-language explainer first.

Summary

ograph is an RDF quad store on redb with a single validated write path. Enrichers reduce operational exports to episodes and emit proposed facts. A gateway checks each batch against an OWL ontology and SHACL shapes, commits it as one named graph, and quarantines what it refuses. Correlation walks a per-application time index to build scored causal chains. Four investigation queries run on native indexes, and everything else is SPARQL 1.1 through Oxigraph’s evaluator over the same snapshot.

1Architecture: one write path, two read paths

Plain-language version: The problem

Nothing writes to the store except the gateway. That single rule is what makes the rest of the system simple to reason about: every stored triple has passed the same checks and belongs to exactly one or more named graphs that say where it came from.

In plain words

An enricher is a translator that may only suggest.

Every tool writes in its own format. Alerts are JSON, metrics are a spreadsheet, chat is a wall of text. An enricher reads one of those formats and turns it into the same kind of short sentence as every other enricher.

It never writes to the graph itself. It hands its sentences to the gateway, like a reporter filing copy with an editor. The name comes from what it does to the graph: it adds to, or enriches, what is already known.

Harvest order

Enrichers run in layers, and each layer can rely on what earlier layers committed. The order is the declaration order of a Rust enum, so the order of [[source]] entries in config.toml does not matter.

  12. news

The catalog goes first because only the catalog may create an application. Every later source refers to applications by name, and the gateway resolves those names against it. Discussions come late because the model step that classifies threads is the only non-deterministic enricher.

Why the catalog comes from ogrep

ogrep is an indexed code-search tool by the same authors. For the catalog layer, ograph runs ogrep --entities . --json inside the catalog repository and turns each service and each dependency it reports into proposed facts. Each fact carries the file and line it was found on as evidence, and each dependency says whether it was declared outright or inferred.

In plain words

ogrep reads the code, so ograph does not have to.

The list of services, and who calls whom, is already written down in a company’s repositories: Backstage catalog files, Docker Compose files, Kubernetes manifests, Prometheus rules. Reading all of those formats correctly is a job of its own, and ogrep already does it. ograph asks ogrep for the answer instead of learning to read them a second time.

It is a division of labour. ogrep knows the code. ograph knows what happened in production. Netflix’s design draws code search as its own box beside the graph, and here that box is ogrep.

It is a hard requirement for this one layer only. Without it the harvest still runs, but the catalog line reports DEGRADED: ogrep not runnable, no applications exist, and the gateway quarantines every fact that names a service.

The unit of writing

An enricher produces a batch: a source name, a stable key (the file path), and a list of proposed facts. The types make some mistakes unrepresentable. A model-proposed fact cannot exist without a confidence, and a confidence cannot be built outside 0 to 1.

ograph-core/src/model.rs
pub struct ProposedFact {
    pub subject: EntityRef,
    pub predicate: NamedNode,
    pub object: Object,
    pub evidence: Vec<EvidenceRef>,   // a source record id, a file:line, or a query
    pub method: Extraction,
}

pub enum Extraction {
    Rule { extractor: String },
    Catalog { catalog: String },
    Llm { model: String, prompt_hash: String, confidence: Confidence },
    Human { who: String },
}

pub enum EntityRef {
    Known(NamedNode),                                  // an IRI the code minted
    Provisional { class: &'static str, name: String }, // a name the gateway must resolve
}

2The data model

Plain-language version: A knowledge graph is a pile of short sentences

The ontology is one Turtle file, ontology/ograph.ttl, in seven modules that follow Netflix’s namespaces: ops for the catalog, evt for events, inc for incidents, disc for discussion threads, corr for correlation, rca for verdicts and harv for provenance. It declares classes, properties with domain and range, and closed vocabularies with a definition per value.

In plain words

RDF is a way to write facts so plainly that any tool can read them.

In RDF every fact is a sentence of exactly three parts: a thing, a relationship, and another thing or a value. “payments-api, depends on, ledger-db” is one fact. Three parts make a triple. There are no tables and no nested records, which is why facts from twelve different tools can live together.

The names in those sentences are IRIs: full names that cannot be mistaken for anything else. “checkout” could be a service, a team or a web page. https://ograph.dev/id/app/checkout is exactly one thing, and id:app/checkout is the short way to write it.

In plain words

An ontology is the rulebook for which sentences make sense.

It says what kinds of things exist and how they may connect. A deployment is a kind of event. “Depends on” joins two applications, never an application and a team. Severity is one of four words. OWL is the standard language such a rulebook is written in.

Without it, a graph accepts anything, and a graph that accepts anything cannot be trusted to answer a question.

An instance: one chain, as stored

A chain is a node, in the way Netflix’s post models it, and its links are ordinary edges to event nodes. This is the top chain of the demo incident, read back with SPARQL.

Identifiers and closed vocabularies

Code mints every IRI, never a model. Data nodes live under https://ograph.dev/id/ and must match one scheme: a lower-case kind, then a slug. An event’s IRI is derived from its content, such as id:ev/alert-ledger-db-ledgerpoolsaturated-1795385980000, so harvesting the same record twice yields the same node.

Eight properties take values from closed lists that the ontology declares with a definition per value: evt:signal (16 values), evt:severity (4), disc:category (8), disc:sentiment (3), inc:status (3), ops:tier (4), rca:state (2) and harv:status (2). The model prompt is generated from the same lists the gateway enforces, so the two cannot drift apart.

Named graphs are the provenance

Each batch commits to its own named graph, and the default graph is the deduplicated union of them all. Asking “says who?” of any triple is a lookup of which graphs hold it. Re-harvesting a file replaces its graph, which makes a harvest idempotent, and deleting a file prunes its graph on the next run.

In plain words

A quad is a triple with a sticker saying which folder it came from.

Picture every source file as a folder of facts. Each fact carries a fourth part, a sticker naming its folder. Three parts plus the sticker make four, hence quad. The folder is what RDF calls a named graph.

The sticker pays off twice. You can always ask where a fact came from. And when a file changes, ograph swaps that one folder and leaves the rest alone. If two folders state the same fact, it survives until both let go of it.

3The store: a quad store on redb

The store is one redb file. redb is a pure-Rust, copy-on-write B-tree with ACID transactions, the same base Netflix chose for its own quad store. ograph imports Oxigraph’s RDF and SPARQL crates but not its storage, which has no extension point and needs RocksDB and a C++ toolchain.

In plain words

A quad store is a filing system built for four-part facts, and an index is the index of a book.

To find every mention of “ledger-db” in a book you do not read each page. You look in the index. A database index is the same idea: the facts are kept sorted, so the ones you want sit next to each other.

The catch is that a sorted list only helps if you know its first part. So ograph keeps the same facts sorted three ways, by subject, by relationship and by object. Whichever part of a sentence you know, one of the three lists starts with it.

One more trick saves space. Names are long and numbers are short, so each name is swapped for a number once, like a coat-check ticket, and the lists store tickets.

Terms become 64-bit ids

Every RDF term is one u64. IRIs, strings and blank nodes go through a dictionary keyed by a 128-bit SipHash of the encoded term, so each term is stored once. Integers, booleans and dateTimes in canonical form skip the dictionary: the value lives inside the id.

The default graph is a reference-counted union

A triple asserted by three harvests is one row in each union table with a count of 3. SPARQL over the default graph therefore never sees a duplicate, and removing one graph decrements counts without scanning the others. A pattern restricted to a named graph scans the fitting union ordering and then confirms membership in gspo or spog. That is why two graph-qualified orderings suffice where Oxigraph keeps six.

The time indexes are why “before” is constant time

SPARQL’s interface to a store is the triple pattern, so a query for “events on this application between two times” must read every event the application ever had and filter. The app_time table has the application and the time as a key prefix, so the same question is one short range scan.

Concurrency and durability

  • Readers use snapshots. A query opens a redb read transaction and sees one consistent state while a harvest commits behind it.
  • Writers are serialised across processes. A harvest or a verdict takes a file lock from its snapshot to its commit, so it never commits facts that were checked against a state another writer has since changed.
  • Every commit is durable. Non-durable commits were measured and rejected: they did not speed up the load, and redb cannot reuse pages freed by them until a durable commit, which doubled the file.
  • An unchanged batch commits nothing. The gateway compares the batch with the stored graph first, so a re-harvest of unchanged files costs reads only.

4The gateway: six checks, in order

Plain-language version: Nothing enters the graph without a check

The gateway takes a batch and returns two sets: accepted triples, which replace the batch’s named graph, and rejections, which replace its quarantine graph. Each rejection is a node with the fact and the reason, and its IRI is a hash of both, so the same refusal on a later run is the same node.

Name resolution

Sources rarely spell a service the way the catalog does. The gateway normalises the name, looks for an exact match on names and declared aliases, and otherwise scores it against every catalog entity of that class with Jaro-Winkler similarity.

In plain words

Jaro-Winkler is a score from 0 to 1 for how alike two spellings are.

“inventry” and “inventory” score close to 1, because they share almost every letter in the same order. It forgives typos well. It also forgives too much: “-uk” and “-eu” differ by two letters at the end of a long name, so two different services look nearly identical. That is why a high score needs the extra rules below.

Incremental SHACL against the store as it will be

In plain words

SHACL is a checklist for what a complete thing looks like.

The ontology says which words exist. SHACL says what a valid thing must have. “Every event has a time.” “A chain has exactly one root cause.” “A confidence is between 0 and 1.” Each rule is called a shape.

Incremental means checking only what this batch touched, the way a proofreader rereads only the pages that were edited instead of the whole book.

Validating a whole store on each batch would not scale, and validating the batch alone would miss violations that only appear when it meets existing data. The gateway does neither. It builds an overlay: the union graph, minus what only the graph being replaced holds, plus the accepted facts, plus the ontology for class reasoning. It then validates only the focus nodes the batch touches.

Removing a fact can break another shape, so the pass repeats until no violation remains; each pass either drops a fact or stops. A bad value that the batch did not propose belongs to another graph, and this batch is not rejected for it.

Hand-written shapes say only what must be present. Domain, range, vocabularies and functional properties are derived from the ontology in code, so they are not written twice.

ontology/shapes.ttl
shape:Chain a sh:NodeShape ;
  sh:targetClass corr:Chain ;
  sh:property [ sh:path corr:leadsTo ;    sh:minCount 1 ; sh:maxCount 1 ] ;
  sh:property [ sh:path corr:rootCause ;  sh:minCount 1 ; sh:maxCount 1 ;
                sh:message "a chain has exactly one root cause" ] ;
  sh:property [ sh:path corr:confidence ; sh:maxCount 1 ;
                sh:minInclusive 0 ; sh:maxInclusive 1 ] .

That last constraint once caught a real bug. Anomaly strength was not capped, so chain confidences exceeded 1, and the gateway quarantined 75 chains from ograph’s own correlator. The SHACL engine is ograph’s own, about 830 lines, because no available crate could validate chosen focus nodes over a custom store. It passes all 98 tests of the W3C SHACL Core suite.

What counts as support for a model’s claim

A model may propose ops:dependsOn from a chat thread. The gateway commits the edge only if the catalog or the traces already assert it. Co-occurring events were tested as a second kind of support, on all 9,900 ordered application pairs of the benchmark, and rejected.

5Detectors: from raw telemetry to episodes

Plain-language version: Keep the episode, leave the raw data where it is

Logs, metrics and traces never enter the graph as records. A detector reads the file, finds episodes, and proposes one event per episode with a pointer to the first raw record. The detectors are online: each point is judged against a trailing baseline, never against a label or a known incident time.

Metrics: a robust z-score with a floor

For each series the detector keeps a baseline from the trailing 300 seconds, leaving out the most recent 10 so that the start of an anomaly does not contaminate it. It uses the median and the median absolute deviation (MAD) rather than the mean and standard deviation, because one outlier barely moves a median.

In plain words

The detector asks one question: how many normal wobbles away is this point?

The median is the middle value of recent history. Call it “normal”. The MAD is how far points usually stray from it. Call it “the normal wobble”. The z-score is the distance from normal, counted in wobbles.

A connection count that sits near 60 and wobbles by 3 is at z = 1 when it reads 63. When it reads 196, it is about 50 wobbles out, and nobody needs a threshold tuned by hand to call that abnormal.

The score of a point. z = (value − median) / scale scale = max( 1.4826 × MAD, 0.01 × |median|, (max − min) / 6 ) An episode opens when z reaches 5, needs 3 anomalous points to count, and closes after more than 2 normal points in a row. Only rises count, except for metrics such as throughput where a drop is as telling. The detector waits for 12 points and 150 seconds of history before judging anything.

The second and third terms of the scale are the floor. A sparse series that is mostly zero has a MAD of 0, and without a floor one routine spike scores like an outage. The first benchmark run scored 0.21 for exactly this reason: a disk metric with a median and MAD of zero produced a z of 1010.

Strength: one scale for every signal

A z-score of 51 and an alert of severity SEV1 must be comparable, so each detector’s raw score maps to a strength between 0 and 1 on a log scale. A z of 5 is 0 and a z of 200 is 1.

In plain words

Drain turns a million log lines into a handful of patterns you can count.

“user 4812 failed login” and “user 977 failed login” are the same message with a different number. Drain blanks out the parts that vary and keeps the template: “user <*> failed login”.

Once lines are grouped by template, “is something wrong?” becomes a counting question: did this pattern suddenly appear three times more often than a few minutes ago?

Template masking matters more than it looks. Product ids such as L9ECAV7KIM once escaped the mask, and one service produced 9,113 distinct templates from what were really 6. Masking upper-case ids that contain a digit fixed it without changing any score.

6Correlation: scored chains over the dependency graph

Plain-language version: A worked example

Correlation runs after every source has been harvested, once per incident. Its output is a batch of corr:Chain nodes that goes through the gateway like any other.

Step 1: candidates

The scope is the incident’s application and everything it depends on, found by a breadth-first walk of ops:dependsOn to depth 4. For each application in scope, one range scan of app_time returns the events in the 30 minutes before the incident. An episode that started earlier but was still under way when the window opened also counts, with a 24-hour lookback.

The walk respects when a dependency began. ogrep dates each dependency by the first commit of the unbroken run in which the catalog repository has held it, and the catalog stores that as an ops:Dependency with ops:validFrom (ontology 1.4). Every walk over ops:dependsOn for an incident takes the incident’s open time and skips a dependency dated later. before and chains list the skipped ones as withheld, and blast --at uses the same rule. A dependency that came in the commit that declared its service gets no date: before that commit the files said nothing about the service, which is no evidence the dependency was absent.

Step 2: score a link

The link from event a to a later event b. known pair (a.kind, b.kind): 0.9 otherwise: 0.6 × proximity + 0.4 × severity(a) proximity = 1 − gap / window, gap = b.at − min(a.until, b.at) Known pairs are DEPLOYMENT to LOG_ERROR, CONFIG_CHANGE to METRIC_ANOMALY, ALERT to INCIDENT and TRACE_FAILED to INCIDENT. All of these are settings in config.toml. With own_degradation, the default, a known pair holds only between two events of one application, or for a link that closes at the incident. A deployment on a callee links to its caller’s errors by the formula, so a change scores as a root only as strongly as its own application degrades.

The gap is measured from the end of the earlier episode. An anomaly still under way when the next event arrives is adjacent to it, with a gap of zero. Measured from the start, a fault that began five minutes before the incident and never stopped scored below a one-point blip seconds before it. Fixing that cut the misses on the benchmark from 12 to 6.

Step 3: search

From each candidate as a root, a depth-first search extends the path through later events, subject to these rules:

  • The next event is on the same application or on one that calls it. Failure flows from a dependency to its callers.
  • The next event is not the same kind on the same application.
  • Every intermediate link scores at least 0.6.
  • A path holds at most 5 events, and the search stops after 2,000 expansions per root.

Each path closes with a link to the incident. A chain’s confidence is the geometric mean of all its links, so one weak link pulls the whole chain down and a longer chain is not penalised for its length. A chain is kept only if both its closing link and its confidence reach 0.6.

In plain words

A chain is only as believable as its weakest link, and the geometric mean respects that.

An ordinary average lets one strong link hide a weak one: 1.0 and 0.2 average to 0.6. The geometric mean multiplies the links and takes the root, which gives 0.45 for the same pair. A story with one shaky step scores like a shaky story.

Depth-first search is how the chains are found: follow one path as far as it goes, back up one step, try the next turn. It is how you would explore a maze with one hand on the wall.

Step 4: rank applications

Each application takes the confidence of its best chain. Sustained, saturated anomalies often tie, so ties break in a fixed order: the chain that passes through more distinct applications, then the earlier root event, then the name. Confidences are compared at nine decimal places so floating-point noise cannot decide a tie.

One rule overrides the scores. The geometric mean favours a suffix: a caller’s chain is often the later part of its dependency’s chain, and it scores higher only because it leaves out the first link. So an application explains another when its chain reaches an event of that application no later than that application’s own best chain begins, through links that each leave an anomaly still under way, from a root of at least SEV2 strength (0.5). It then ranks above every application it explains, whatever their scores. A change is a point in time, never under way, so it explains nothing. On a fresh 150-case distractor suite this took chain rank 1 from 114 to 143 correct, 29 better and 0 worse, and left RCAEval rank 1 identical on all 90 cases. own_degradation = false restores the earlier ranking.

Ranking also marks, without reordering. An event whose series (same application, signal kind, and metric or log template) started at least 2 episodes in the window before the incident carries chronic in before, on chain events in chains, in why, in the lab and in the MCP tools. No score changes. With the mark, an agent on Haiku using the MCP tools named the right root on 0.77 of held-out RCAEval runs, against 0.34 without it.

A chain’s IRI is 64 bits of a hash of the incident and the root event. It does not contain the rank, so a verdict recorded against a chain stays attached to the root it judged when a later harvest reorders the ranking.

Why the window is 30 minutes

Netflix’s post uses 10 minutes. On the benchmark that fails as soon as the incident opens late, because the root event falls outside the window.

Propagation ranking is the alternative for a team that must keep a short window. It scores each application as 0.4 × its strongest anomaly + 0.5 × its best chain + 0.1 × the share of its callers that show a later event. A grid of 206 weight combinations tuned on one repetition gave no gain on the held-out ones, so the shipped weights are not fitted to labels.

7Verdicts and investigation memory

Plain-language version: A chain is a guess until a person says otherwise

A verdict is the only write that does not come from a source file, and it still goes through the gateway, with Extraction::Human as its method and the person’s name attached. An accepted verdict writes inc:cause from the incident to the chain’s root event.

Telemetry expires, and a cause must not expire with it. The verdict node therefore copies what it judged: the root event’s class, application, time and signal. The root event itself gets nothing extra, so once its telemetry is retired it is no longer a candidate for correlation, while the recorded cause still reads correctly.

Similarity is a cosine over onset signatures

An incident’s signature is a sparse vector. Its dimensions are (application, signal kind) pairs, and each value is the sum of the strengths of that pair’s events in the 15 minutes before the incident. Two incidents are compared by the cosine of their signatures, and similar returns past incidents by descending similarity with their accepted causes and mitigations.

In plain words

Two incidents are alike when the trouble is spread across services in the same proportions.

Write each incident as a list: how much alerting on ledger-db, how much error logging on payments-api, and so on. Cosine similarity compares the shape of two such lists and ignores their size.

A small outage and a large one with the same pattern score near 1. Two outages of the same size on different services score near 0.

SPARQL through one adapter

In plain words

SPARQL is to a graph what SQL is to tables: you describe the pattern, and the database fills in the blanks.

A query is a sentence with holes in it. ?app ops:dependsOn id:app/ledger-db asks “what goes in the blank?” and the answer is every application for which that sentence is true. Names starting with ? are the blanks.

Add a second sentence that reuses a blank and you have a join. Add a + after a relationship and it means “one or more steps”, which is how one line finds everything that depends on a service, directly or through others.

Oxigraph’s evaluator, spareval, runs SPARQL over any type that implements one trait, QueryableDataset. Its central method takes a quad pattern with optional subject, predicate, object and graph and returns an iterator of matching quads as internal ids. ograph implements it over a snapshot in one module, the only place that touches the pinned 0.x crates. Constants that a query introduces and the store has never seen get ephemeral ids, with bit 63 set, that live for that query alone.

examples/demo
$ ograph sparql 'SELECT ?app (COUNT(?e) AS ?events) WHERE {
      ?e evt:on ?a ; a evt:Alert . ?a ops:name ?app
    } GROUP BY ?app ORDER BY DESC(?events)'

$ ograph sparql 'SELECT ?app WHERE { ?a ops:dependsOn+ id:app\/ledger-db ; ops:name ?app }'
# every application that depends on ledger-db, through a property path

A wrong name is an error, not an empty answer

In SPARQL, a query that uses a predicate nobody declared returns no rows, which reads as “there are none”. For an agent that is a silent failure. Before running a query, ograph checks every name in its own namespaces against the ontology and refuses an undeclared one, suggesting the nearest declared name by Jaro-Winkler similarity. ops:dependOn yields “did you mean ops:dependsOn?”.

The same check catches a subtler trap. Each node stores only its most specific type, so matching the superclass evt:Event finds nothing. The error lists the subclasses to match instead. Over every predicate and class stored in the demo graph, the check produced no false rejections.

Serving

ograph serve keeps the store open and answers line-delimited JSON-RPC over TCP. It writes its address to .ograph/serve.json so clients find it without configuration. It polls the source files every 5 seconds and re-harvests on change. With --mcp the same tools speak MCP over stdio: before, chains, blast, similar, code, suspects, why, uses, news, sparql, resolve, cite_check and verdict. Calls took 0.1 to 1.7 ms each. SPARQL through these tools is read-only.

The model path

ograph contains no provider code and holds no credentials. For extraction it runs a configured command, by default pi, with the prompt on standard input and reads JSON from standard output. The cache key is the content hash of the input, the model and the prompt hash, so a re-harvest of unchanged threads makes no calls and yields the same triples. A failed call marks that harvest as degraded and does not block the others.

Why Oxigraph’s crates, and not Neo4j or another graph database

In plain words

ograph is one small program and one file. A graph database is a server someone has to run.

The difference is the one between SQLite and a database server. Neo4j, Apache AGE and HugeGraph are services to install, secure, upgrade and keep alive. ograph opens a file in a few milliseconds, answers, and exits. That matters on a laptop, in a CI job, and on a corporate network where every new server needs approval.

The second reason is the data model. Those databases store property graphs and speak Cypher or Gremlin. ograph’s design rests on RDF: an ontology, named graphs for provenance, SHACL for validation, SPARQL for questions. None of that is built into a property graph database, so it would all have to be rebuilt on top.

Oxigraph is an open-source RDF database written in Rust. ograph borrows its two hardest parts to get right, the RDF parsers and the SPARQL engine, and writes its own storage underneath, because the questions ograph asks most need indexes Oxigraph does not have.
